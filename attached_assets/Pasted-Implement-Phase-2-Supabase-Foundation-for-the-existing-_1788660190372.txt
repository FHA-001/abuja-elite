**5. Administrator authorization and RLS**

Implement a small administrator allowlist tied to auth.users, preferably in a private schema outside the exposed Data API schemas.

Required behavior:

* Authentication alone does not grant administrator privileges.
* Public signup cannot create an administrator.
* User-editable metadata must not control administrator authorization.
* Anonymous and ordinary authenticated users cannot modify the allowlist.
* Initial administrator provisioning must happen through a trusted dashboard/SQL workflow.
* Do not create a public “make me admin” endpoint.

Provide a reusable authorization helper that checks the current authenticated user. Avoid recursive RLS policies. Any SECURITY DEFINER function must use a safe search_path, fully qualified references, and explicitly restricted execution privileges.

If the frontend needs an authorization RPC, expose only the current caller’s administrator status, with no arbitrary user-ID lookup.

Enable RLS on every application table and define explicit grants and policies:

* Anonymous and ordinary authenticated users can read published public content only.
* They cannot create, edit, delete, feature, or publish content.
* Stories must also satisfy the chosen publication-time rule.
* Public settings access must enforce the visibility field.
* Applications, contact messages, event interests, and newsletter records must not be publicly readable.
* Authorized administrators can manage content and review submissions.
* Allowlist administration remains outside the browser CMS for this phase.

Public submission endpoints are deferred to Phase 4. Leave anonymous submission-table writes denied now.

Document the planned Phase 4 submission boundary: server-side validation, spam protection, persistent rate limiting, duplicate handling, controlled fields, and non-revealing responses. Do not add unrestricted INSERT policies as a shortcut.
